# x402 payment channels

[中文](X402.zh.md)

Without an API key, a client (local proxy or x402 SDK) signs payment vouchers with its wallet key. API keys instead bill the [prepaid pool](PREPAID_POOL.md). The gateway implements the Foundation's [batch-settlement scheme](https://github.com/x402-foundation/x402/blob/main/specs/schemes/batch-settlement/scheme_batch_settlement_evm.md), using `x402BatchSettlement` at `0x4020074e9dF2ce1deE5A9C1b5c3f541D02a10003` (CREATE2, already deployed on Monad; not deployed by this project). Current SDK dependencies are `@x402/core` and `@x402/evm` 2.29.0.

## Payment paths

| | API key (default) | Native x402 (advanced) |
| --- | --- | --- |
| Funds | Wallet's shared prepaid pool | Wallet's individual channels |
| Signatures | Wallet authorizes automatic payment during setup | Client signs a voucher per call |
| Client | Any compatible OpenAI / Anthropic / Responses client | Local proxy or x402 SDK |
| Concurrency | 128 per key (`API_KEY_MAX_CONCURRENCY`), within pool availability | Channel count (`X402_MAX_CHANNELS_PER_PAYER`) |
| Transactions | Settler sends `settle` (debit + refill) | Facilitator sends claim / settle |

Keys created between 2026-10-23 and 10-26 had a channel each. They now bill the pool; refund their old channel balances with `POST /v1/keys/:id/refund` or when revoking the key.

## Native x402 request flow

1. Call `/v1/chat/completions`, `/v1/messages` or `/v1/responses` without credentials. The gateway validates/prices the request and returns `402`. Base64 JSON in `PAYMENT-REQUIRED` includes `amount` (ceiling in micro-USDC), `payTo` (Treasury), `extra.receiverAuthorizer` (Settler), `extra.withdrawDelay` and `extra.minDeposit`. The protocol-specific error is `PAYMENT_REQUIRED`; `details.x402.accepts` is a readable copy.
2. Sign `Voucher(channelId, maxClaimableAmount = cumulative + amount)` and retry with `PAYMENT-SIGNATURE`. If channel balance is short, the SDK packages a deposit authorization and voucher into a `deposit` payload.
3. With a fresh chain mirror (five minutes), the gateway verifies locally; otherwise facilitator `/verify` checks chain state. A verified request registers a pending settlement. One request can be active on a channel at a time.
4. Call the upstream, calculate actual model cost plus service fee and record only that amount through a settlement override, bounded by the ceiling. Non-streaming responses carry `PAYMENT-RESPONSE`. `gateway.x402` contains `charged_atomic`, `cumulative_atomic`, `ceiling_atomic`, `transaction` (when depositing) and `payment_response`.
5. SSE cannot add headers after streaming starts, so the final data chunk carries `gateway.x402.payment_response`. The next SDK request receives a corrective 402 containing the server's cumulative amount and its own signed voucher. The client checks chain state and re-signs; use `toClientEvmSigner(account, publicClient)`.

A provider rejection before charging (`chargeCertainty: not_charged`) cancels the reservation for free. Unknown usage, including interrupted streams, timeouts or failures after provider dispatch, charges the signed ceiling (`charged_from = ceiling`) and records the error. Non-streaming calls continue after client disconnect and bill actual usage if it becomes available.

## Concurrency: channel pool

Vouchers are cumulative: voucher N+1 depends on the settled cumulative amount after N. A channel therefore handles one request at a time. Different salts create separate channels, deposits and cumulative balances for one wallet.

- `clients/x402-proxy` starts with one channel and opens more when all are busy, up to `X402_MAX_CHANNELS_PER_PAYER` (128 by default; proxy `--max-channels`). Salts persist in `~/.router3/salts.json` across restarts.
- Deposits are `max(minDeposit, current shortfall)`. Default `X402_MIN_DEPOSIT_USDC` is 0.1 to limit idle funds per channel.
- The gateway rejects a 129th channel deposit with `402 X402_CHANNEL_LIMIT`.
- Several channels can be claimed in one transaction and transferred with one settle, amortizing transaction overhead. Gas still depends on batch size.

## Channel lifecycle

- **Open:** automatic deposit on first call, or console deposit through `POST /v1/x402/deposit` (0.000001 USDC advances the voucher).
- **Accumulate:** retain the latest voucher and actual cumulative charge in `private.x402_channels`. PostgreSQL row-locked SDK ChannelStorage supports replicas.
- **Claim:** collector scans every `X402_CLAIM_INTERVAL_SECONDS` (600). Claim when unclaimed usage reaches `X402_CLAIM_MIN_USDC` (1), idle time exceeds `X402_CLAIM_IDLE_SECONDS` (86400), or on-chain `pendingWithdrawals` shows a withdrawal. Settler signs `ClaimBatch`; the facilitator submits `claimWithSignature` and pays gas, then `settle(Treasury, USDC)` transfers claimed funds.
- **Refund:** `GET/POST /v1/x402/refund`, payload `type: refund`, a zero-cost voucher (`maxClaimableAmount` = cumulative charge) and optional `amount`. The gateway signs Refund/ClaimBatch; the facilitator claims owed usage and refunds in one transaction. The channel record is removed; later calls open a new channel. Refunds are one transaction per channel: proxy `refund --all` signs sequentially; the console asks the wallet to sign each.
- **Withdraw:** the user sends `initiateWithdraw(config, amount)` with their own MON. After `withdrawDelay` (default 86400 seconds; contract range 900–2592000), call `finalizeWithdraw`. Collector claims as soon as it sees the request; the contract caps withdrawal at unclaimed balance.

## Security boundaries

- Only the signer holds the Settler private key. `signerRef: x402-authorizer-v1` signs only `ClaimBatch` / `Refund` EIP-712 types for the fixed contract and chain 143. Each claim's `totalClaimed` is bounded by mirrored actual charges; `maxClaimableAmount` must match the saved voucher. Refunds cannot exceed deposit minus actual charge. For this x402 path, the facilitator sends transactions/pays gas; the same Settler separately needs MON for pool transactions.
- `AUTH_ALLOWED_ADDRESSES` restricts `channelConfig.payer` before state changes.
- `X402_REQUEST_LIMIT_USDC` (5) bounds each signed ceiling; excess returns `402 X402_REQUEST_LIMIT`.
- Rate limits are bucketed by channel ID.
- A wallet's first OpenRouter call creates a remotely limited key using the management key. Pool wallets follow their daily limit; otherwise `payerKeyLimitUsd` applies.
- The default facilitator, `https://x402-facilitator.molandak.org`, verifies signatures, reads chain state and relays contract calls; it cannot redirect funds. During an outage, fresh mirrors can verify locally, while deposits/claims/refunds wait. Stale mirrors and ERC-1271 paths requiring remote checks are blocked. Set `X402_FACILITATOR_URL` to a self-hosted `@x402/core` facilitator with a MON-funded relay wallet; the fork test demonstrates this setup.

## Configuration

| Variable | Purpose |
| --- | --- |
| `TREASURY_ADDRESS`, `SETTLER_ADDRESS`, `SETTLER_SIGNER_URL`, `SETTLER_SIGNER_BEARER_TOKEN` | Treasury, Settler and signer service credentials for API/collector |
| `X402_FACILITATOR_URL`, `X402_FACILITATOR_TIMEOUT_MS` | Facilitator URL and timeout (90 seconds) |
| `X402_WITHDRAW_DELAY_SECONDS` | New-channel withdrawal delay (86400) |
| `X402_MIN_DEPOSIT_USDC`, `X402_REQUEST_LIMIT_USDC`, `X402_MAX_CHANNELS_PER_PAYER` | Minimum suggested deposit (0.1), call ceiling (5), channels/wallet (128) |
| `API_KEY_MAX_CONCURRENCY` | Concurrent calls per API key (128) |
| `API_KEY_REQUEST_LIMIT_USDC` | API key hold ceiling (50); native x402 uses `X402_REQUEST_LIMIT_USDC` |
| `X402_CLAIM_MIN_USDC`, `X402_CLAIM_IDLE_SECONDS`, `X402_CLAIM_INTERVAL_SECONDS` | Collector claim policy |
| `STREAM_REQUEST_TIMEOUT_MS` | At most 570000; SDK pending reservations last up to ten minutes |

Data: `private.x402_channels` (mirror), `private.x402_requests` (ceilings, charges, cumulative totals, usage, `charged_from`) and `private.x402_settlements` (chain operations). Reconciliation and `metrics_x402()` use these records.

## Endpoints

- `GET /v1/x402`: network, asset, Treasury/authorizer, withdrawal delay, minimum deposit, request/channel limits, contracts, facilitator and readiness.
- `GET /v1/models`: callable models in OpenAI format without authentication.
- `POST /v1/x402/deposit`, `GET|POST /v1/x402/refund`: described above.
- `GET /v1/x402/channels`, `GET /v1/x402/channels/:id/requests`: session-authenticated access to the wallet's self-signed channels and calls.
- API keys, pool setup, key limits, legacy refunds, revocation and call history: [HTTP API](API_REFERENCE.md).

## Clients

- Local proxy: `node clients/x402-proxy/cli.mjs serve --gateway https://router3.ai`, then `OPENAI_BASE_URL=http://127.0.0.1:8402/v1`. Commands: `refund --all`, `status`. Load the key from `ROUTER3_PAYER_KEY` or `ROUTER3_PAYER_KEY_FILE`.
- SDK: `@x402/fetch` with `@x402/evm/batch-settlement/client`. A scheme instance holds one channel; an agent can use a separate session authorizer (`payerAuthorizer`).

## Limitations

- Native x402 concurrency uses multiple separately funded channels. API keys share a wallet pool and do not have the one-request-per-channel restriction.
- API key trust/limits are described in [prepaid pool authorization](PREPAID_POOL.md#authorization-limits); new keys do not create voucher-signing private keys.
- SSE needs a corrective 402 round trip and a client able to read chain state.
- Unknown usage is charged at the ceiling without later usage-based refunds.
- Smart-wallet payers with zero `payerAuthorizer` require facilitator ERC-1271 checks on every call; no local fast path.
- Refunds are one transaction/signature per channel in browser wallets.
